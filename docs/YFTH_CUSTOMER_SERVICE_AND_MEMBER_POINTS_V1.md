# 御方通和客服与 C 端会员积分 V1

## 1. 冻结边界

本阶段不删除或改写既有平台董事、大区总监、省级、地级、县级合伙人身份及其工作台。新增的 `customer_service` 是独立经营身份，不是合伙人别名，也不承接合伙人收益。

B1、合伙人现金佣金保持现状。仅 C 端 C1 的普通商城直推奖励及会员套餐 15% / 25% / 60% 奖励改为商城积分；C 端不再拥有现金收益、结算或提现入口。

## 2. 客服模型

- 总部在“客户与会员 -> 用户经营身份”中授予客服，并选择其服务的 B 端门店。
- 一名客服可服务多家 B 端门店；同一门店同一时间只有一名客服。
- 客服无上级、无收益、无结算、无提现权限。
- 客服工作台只返回已分配门店、门店基础资料及脱敏后的店长联系方式，不查询 C 端客户、推荐关系或财务数据。
- 门店绑定重复提交幂等；门店已由其他客服负责时拒绝。解除最后一家门店后，客服经营身份同步停用。
- 前端身份仅决定工作台入口，服务端身份和门店绑定始终重新校验。

## 3. C 端积分模型

Automatic Commission 继续负责规则快照、观察期、幂等、入账和退款冲正。到期入账时：

1. C1 金额按 `1 元奖励 = 1 积分` 写入 `yfth_member_points_account/ledger`；
2. 同步增加 CRMEB `user.integral`，商城仍使用原积分下单、订单快照和退款返积分能力；
3. B1 金额继续进入原 B1 现金佣金账本；
4. C1 不再写 `yfth_user_commission_account`，也不再增加门店 C1 代付责任；
5. 奖励冲正优先扣回可用积分，不足部分记录积分债务，并由后续 C1 奖励先行抵扣。

历史现金记录保留只读审计。总部的受控转换只处理尚未支付的 `available_cent + frozen_cent`，取消对应待处理 C1 现金结算，不转换 `withdrawn_cent`，避免已支付现金重复补发积分。

## 4. 抵扣范围

- 兑换价值固定为 `1 积分 = 1 元`。
- 总部配置全局最大抵扣比例和最低现金金额，最低现金不得低于 0.10 元。
- 仅普通 C 端商城商品可使用。
- 采购商品、9800 会员套餐、开店服务和运费不参与积分抵扣。
- 商品级规则可关闭某一商品的积分使用，正式商品 ID 不写死在前端。
- 订单取消、全额或部分退款继续由 CRMEB 原订单退款链按订单积分快照返还实际使用积分。

## 5. 数据表

- `yfth_member_points_account`：C1 推荐积分的权威分币账户及整数积分发行、债务投影。
- `yfth_member_points_ledger`：不可变且按来源唯一的积分流水。
- `yfth_member_points_config`：全局抵扣比例、现金底线及启用状态。
- `yfth_member_points_product_rule`：商品级启停覆盖。
- `yfth_customer_service_store_binding`：客服与 B 端门店当前绑定。

## 6. 发布门禁

发布前必须执行 PHP 语法、专用 Contract、隔离 MySQL 8 migration 生命周期、积分/客服真实流、Admin/H5/mp-weixin 受影响构建、敏感信息扫描和 `git diff --check`。生产只能执行正向 migration；历史 C1 余额转换必须由总部显式触发并先完成数据库备份。

本阶段不包含真实生产迁移、历史余额转换、生产部署或微信平台上传。
